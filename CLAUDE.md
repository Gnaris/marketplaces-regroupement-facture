# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Chrome MV3 extension (vanilla JS, no build step, no tests, no package manager). On an order-details page of one of nine B2B fashion / jewelry marketplaces, it adds a "Regrouper la facture" button that fetches the order via the site's API and renders an aggregated table grouped by `(catégorie, prix unitaire)` plus the shipping / billing addresses extracted from the order.

Supported sites (`site` codes used throughout the code):
- `pfs` — wholesaler.parisfashionshops.com
- `efp` — wholesaler.efashion-paris.com
- `aks` — *.ankorstore.com
- `faire` — www.faire.com (brand-portal / seller side)
- `mc` — web.mc.app + mc2-h5.dokkr.net (Microstore — seller-side B2B order portal)
- `oc` — www.orderchamp.com (Orderchamp — supplier backoffice)
- `shopify` — admin.shopify.com (Shopify admin, merchant-side, per-store via `/store/{storeName}/orders/{id}`)
- `bj` — beliandjolie.com (Beli & Jolie — own admin, via `/admin/commandes/{cuid}`). Also matches `localhost:3000` for local dev.
- `bm` — www.bijouxmysteres.fr (Bijoux Mystères — own admin, via `/admin/commandes/{oid}`). API on a different subdomain (`server.bijouxmysteres.fr`), not same-origin.

## Developing & loading

There is no build. To test changes: `chrome://extensions` → enable Developer mode → "Load unpacked" → select this folder. After editing, click the reload icon on the extension card; for `content.js` / `modal.css` changes also reload the order page. For `background.js` changes use the "service worker" link on the card to inspect the worker.

Bump `manifest.json` `version` when shipping.

## Architecture

Three layers, talking via `chrome.runtime` messages and (for PFS / Shopify / MC / Faire) `window.postMessage`:

1. **`content.js`** (runs on each order page at `document_start`) — detects `site` from `location.hostname`, extracts `orderId` from the URL with a site-specific regex, injects the floating button, and on click sends a `FETCH_ORDER` message to the background. A `MutationObserver` re-injects the button after SPA navigations. Parsing of the API response and modal rendering both live here.

2. **`background.js`** (service worker) — single `chrome.runtime.onMessage` listener that branches on `message.site` and calls the right endpoint:
   - `pfs` → `GET https://wholesaler-api.parisfashionshops.com/api/v1/orders/{id}` with the captured `Authorization` header.
   - `efp` → `POST https://wapi.efashion-paris.com/graphql` with the inlined `EFP_QUERY` (`commandeById`), `credentials: "include"`. The query also pulls `acheteur` (contact name, VAT, EORI, email) and `adresseFacturation` (street, postal code, city, country) so `parseEfp` can build the billing block.
   - `aks` → **two parallel fetches** via `Promise.all`: `/order-items?include=orderedProduct` for items and `/orders/{id}` (no path suffix) for the shipping address and retailer business info (VAT / tax number). The response is `{ items, detail }`; `parseAks` consumes both. The `apiBase` is `location.origin` from the content script, so it follows the user's country subdomain. `credentials: "include"`.
   - `faire` → `GET https://www.faire.com/api/brand-order/{id}/details`, `credentials: "include"`. The `id` is a brand-order token like `bo_xxx`. **Addresses are not in this response** — they come from a separate `customer_details` call intercepted by `injected-faire.js` (see below).
   - `mc` → **does not fetch anything**. Microstore's order-detail endpoint (`api2.dokkr.net/index.php/pluginsWeb/orderInfo/{id}?key=...`) requires a per-session `key` query param that's only generated by the host app at runtime, and the order detail opens as a side panel without changing the URL. Instead we **intercept** the response in the page world via `injected-mc.js` (monkey-patches `fetch` + `XHR`), `postMessage` it back to `content.js`, and the content script forwards it to `background.js` via `SAVE_MC_ORDER`. The service worker caches the latest response per `sender.tab.id` in `lastMcOrders` (in-memory `Map`, cleared on tab close). When the user clicks the floating button, the content script asks the worker for the cached payload via `GET_MC_ORDER`. So the worker never reaches the Microstore API itself.
   - `oc` → **does not fetch anything either**. Orderchamp's order detail page is server-rendered HTML, so `parseOc` reads the products and addresses directly from the DOM at click time. No background round-trip needed.
   - `shopify` → `POST https://admin.shopify.com/api/shopify/{storeName}?operation=OrderRegroup` with the inlined `SHOPIFY_QUERY` (Admin GraphQL), `credentials: "include"`. Requires three things from the content script: the `orderId` (numeric, from URL), the `storeName` (also from URL), and a `X-CSRF-Token` header captured by `injected-shopify.js` (see below). Headers also include `Shopify-Proxy-Api-Enable: true` and `Apollographql-Client-Name: core` — Shopify's admin proxy requires both. The query asks for `billingAddressMatchesShippingAddress` so `parseShopify` can render the shorthand "Identique à l'adresse de livraison" instead of duplicating the address block.
   - `bj` → `GET {apiBase}/api/admin/commandes/{id}/regroup`, `credentials: "include"`. `apiBase` is `location.origin` from the content script (so it works on both `https://beliandjolie.com` and `http://localhost:3000`). Endpoint lives in the Beli & Jolie Next.js app (`app/api/admin/commandes/[id]/regroup/route.ts`), auth by NextAuth session cookie (admin only), and returns the already-shaped `{ orderNo, subtotalHT, items: [{categorie, prixUnitaire, quantite}], shipping, billing }`. Category comes from `Product.category.name` joined via `productRef → Product.reference`. **The endpoint intentionally does NOT expose `saleType` / `packQty`** — those raw fields would leak internal schema. Instead, `parseBj` reads the admin page's DOM to detect PACK lines (see `readBjPackInfoFromDom` below) and matches them to the API items by `(qty, unitPrice)`.
   - `bm` → **does not fetch from the service worker**. API is `GET https://server.bijouxmysteres.fr/api/orders/{id}` on a different subdomain than the admin page (`www.bijouxmysteres.fr`), and the API responds with `Access-Control-Allow-Origin: *` without `Allow-Credentials: true`. That combo blocks credentialed requests from both the service worker AND the content script isolated world, so we do the fetch from the **page world** via `injected-bm.js` (see below) and postMessage the response back. Returns the raw order document `{ data: { orderNumber, totalHT, totalTTC, items: [{unitPrice, quantity, categoryName, name, …}], shippingAddress, billingAddress, customer: {companyName, contactName, siret, vatNumber, email, phone, …} } }` — item shape is close to `bj` but `unitPrice` / `quantity` (English) instead of `prixUnitaire` / `quantite`, and addresses come from two sources: the address block (street/zip/city/country/phone) plus `customer` (company/contact/SIRET/VAT/email).

   The host's API origins are declared in `manifest.json` `host_permissions` so the service worker can hit them; without that, the fetch is blocked.

3. **`injected.js`** (PFS only, declared in `web_accessible_resources`) — runs in the **page world** (content scripts run in an isolated world and cannot read the page's in-memory auth token). It monkey-patches `window.fetch` and `XMLHttpRequest` to sniff the `Authorization` header on calls to `wholesaler-api.parisfashionshops.com`, then forwards it to the content script via `window.postMessage({ source: "pfs-regroup", type: "AUTH_TOKEN", token })`. The content script caches this token and forwards it to the background. EFP and Ankorstore don't need this because their APIs accept cookie auth via `credentials: "include"`.

   Consequence: on PFS, the user must have triggered at least one API call (typically by loading the page while logged in) before the button works. The error message "Connexion non détectée. Rechargez la page (F5)…" is the surface for this.

4. **`injected-mc.js`** (Microstore, declared in `web_accessible_resources`) — same page-world injection pattern as `injected.js`, but it sniffs the **full response body** of `pluginsWeb/orderInfo/` calls rather than a header. The Microstore content script is declared with `all_frames: true` in `manifest.json` because the API request happens inside an iframe (`mc2-h5.dokkr.net`) embedded in `web.mc.app` — both frames need the sniffer, but only the top frame (`web.mc.app`) shows the button (`if (!isTopFrame) return;` after wiring up the listener). Site detection accepts both hosts: `host === HOST_MC || host.endsWith(".dokkr.net")`.

5. **`injected-faire.js`** (Faire, declared in `web_accessible_resources`) — same pattern again, but for Faire's `/api/crm/brands/customer-details?retailer_token={retailerToken}` endpoint (URL live-verified 31/08/2026; historical variant `/api/v3/crm/{brandToken}/customer_details` kept as fallback via a second regex). Faire's brand-order endpoint does NOT include the retailer's addresses, but opening the order in the brand portal fires `customer-details` — we intercept that response and cache it in `cachedFaireCustomer` (a content-script-local variable, not in background). **Critical**: the capture regex is strict (must match the exact endpoint path) because nearby endpoints like `/api/crm/brands/customer-order-notes` return small payloads (`{brand_customer_token: …}`) that would overwrite the good data if a broad "any URL containing customer/retailer" pattern were used. `parseFaire(json, customerData)` uses the cached customer to build the shipping (`default_shipping_address`) and billing (`faireBillingFields` — see address policy below) blocks. Like PFS, this means **the order page must be loaded once before the button works** (opening the order from the list is enough — F5 alone may not re-trigger the request); otherwise the addresses are silently omitted and a `console.log` warns to reload.

6. **`injected-shopify.js`** (Shopify, declared in `web_accessible_resources`) — same page-world pattern as PFS's `injected.js`, but sniffs the `X-CSRF-Token` request header on calls to `admin.shopify.com/api/`. Patches both `fetch` and `XMLHttpRequest.setRequestHeader`, forwards the token via `window.postMessage({ source: "shopify-regroup", type: "CSRF_TOKEN", token })`. Content script caches in `cachedShopifyCsrf` and also has a DOM fallback (`getShopifyCsrfToken` reads `<meta name="csrf-token">` / `<input name="authenticity_token">`). Same UX consequence as PFS / Faire: navigate the Shopify admin once so a CSRF-bearing request fires before clicking the button, otherwise the "Jeton CSRF Shopify pas encore capté…" error is shown.

7. **`injected-bm.js`** (Bijoux Mystères, declared in `web_accessible_resources`) — page-world script, but unlike the other injected scripts it does **not** intercept anything at page load. Instead it listens for `window.postMessage({ source: "bm-regroup", type: "FETCH_ORDER", orderId, requestId })` from the content script and **performs the actual API fetch** to `server.bijouxmysteres.fr/api/orders/{id}` from the page context (so cookies for `.bijouxmysteres.fr` flow same-site and the ACAO=* + credentials CORS restriction doesn't apply). It replies with `window.postMessage({ source: "bm-regroup", type: "FETCH_ORDER_RESULT", requestId, ok, data|error })`. The content script correlates request/response via `requestId` (via the `bmPendingFetches` Map) and uses a 15 s timeout in case the injected script never loads.

The content script also exposes an `isExtensionContextAlive()` guard (`chrome.runtime?.id`) at the top of both click handlers, and wraps every `chrome.runtime.sendMessage` in a synchronous `try/catch`. This is because when the extension is reloaded while a tab is still open, the old content script keeps running but `chrome.runtime.sendMessage` throws synchronously with "Extension context invalidated". The guard surfaces a clear "L'extension a été rechargée. Rechargez la page (F5)…" message instead of an uncaught exception in the errors pane.

## Aggregation contract

All nine parsers normalize into the same shape consumed by `showModal`:

```js
{ rows: [{ categorie, prixUnitaire, quantite }, ...],
  orderInfo: {
    orderNo,
    totalVerif,
    addresses: [
      { title: "Adresse de livraison" | "Adresse de facturation",
        fields: [{ label, value }, ...] }
    ]
  } }
```

Rows are merged via `addRow(map, cat, price, qty)` using the key `cat + "||" + price.toFixed(4)` — so two lines with the same category but a 0.0001 € price difference become two rows. If you change rounding here, also change it everywhere prices are read.

Addresses are built field-by-field via `pushField(fields, label, value)` (skips empty values, trims whitespace). The modal renders each block as a `<dl>` with `<dt>label :</dt><dd>value</dd>` rows in a 140px-label grid. A field with `label: null` is rendered as a single italic note across the row — currently used for MC's billing placeholder (`Voir l'iPad`, since Microstore's order endpoint does not expose billing). Per-site address policy:
- `pfs`, `efp`: **billing only** (shipping is on the shipping label PDF the platform already produces, so it would be redundant).
- `aks`: **shipping only** (built from `data.attributes.shipping.shippingAddress` + `retailer.business` for VAT / tax number).
- `mc`: **shipping** from `client_info`, **billing** = literal note "Voir l'iPad" (the user explicitly requested this — the endpoint doesn't reliably expose billing).
- `faire`: **shipping** (`default_shipping_address`, built by `faireAddrToFields`) + **billing** (built by `faireBillingFields`). Live-verified 31/08/2026: the `customer-details` payload does NOT include a `retailer_details.address` sub-object — the retailer's legal address is the same as the shipping address in practice. `faireBillingFields(rd, bcv, shipping, storeName, contactName)` therefore builds the billing block from `default_shipping_address` (fallback) merged with any address fields that might appear at `retailer_details.*`, plus the store name from `brand_customer_view.store_name` and the contact from `default_shipping_address.name`. **SIRET / N° TVA / EORI / email are NOT exposed by the endpoint** — the candidate field lookups (`vat_number` / `eu_vat_number` / `tax_registration_number` / `tax_id_number`, `siret` / `registration_number` / `business_registration_number`, `email` / `contact_email`) are kept as defensive placeholders in case Faire adds them later. The full `customerData` is `console.log`'d on every open to help detect future schema additions.
- `oc`: **shipping + billing**, parsed from the DOM by `parseOcAddresses` (walks siblings after `<strong>Adresse de livraison/facturation</strong>` until `<hr>` or next `<strong>`, then `ocLinesToFields` heuristically classifies lines: special `Numéro de TVA:` / `Numéro d'enregistrement:` are extracted first, then a `^(\d{2,6}[A-Za-z]{0,3})\s+(.+)$` regex finds the postal-code+city line, lines before it become company / contact / address, line after becomes country).
- `shopify`: **shipping + billing**. Both built by `shopifyAddrToFields` from the GraphQL `shippingAddress` / `billingAddress` objects. If `billingAddressMatchesShippingAddress` is `true`, the billing block is replaced by a single italic note "Identique à l'adresse de livraison" (label-less row) to avoid duplication. `address2` becomes a "Complément" line. Country falls back to `countryCodeV2` if `country` is missing.
- `bm`: **shipping + billing**. Both built by `bmAddrToFields` — the address block provides only `street/zip/city/country/phone`, so the company/contact/SIRET/VAT/email fields all pull from `data.customer` (shared between the two blocks). If `shippingAddress` and `billingAddress` match on `street/zip/city/country`, the billing block collapses to the italic "Identique à l'adresse de livraison" note (same shorthand as Shopify).

Per-site quirks the parsers handle:
- **PFS** `parsePfs`: walks `items_by_brand[].products[].items[]`. Items with `type === "PACK"` count as `qty_validated * pieces`. Category is `product.category.labels.fr`.
- **EFP** `parseEfp`: skips `ligne.corbeille === 1` (trash). Unit price = `prixLigne / quantite_total`. `prixLigne` is the actual line subtotal at the time of order (what the buyer was charged); the sibling fields `prix` / `prixReduit` are catalogue prices and can diverge from what was actually invoiced if the vendor changed them after the order — don't use them as a fallback, that would silently re-introduce the wrong total. Category comes directly on the ligne.
- **AKS** `parseAks`: Ankorstore has no category field, so `detectCategory(name)` infers one from the product name with French regexes (boucles d'oreilles, créoles, bracelet jonc/charm, bague d'orteil/ajustable, etc.). Prices arrive as cents in `unitPrice.amount` — divide by 100. Products are in `included[]` with `type === "ordered-products"`, joined to items via `relationships.orderedProduct.data.id`. When adding a new heuristic, put more-specific patterns before more-general ones (the function returns on first match).
- **Faire** `parseFaire`: walks `items[]`. Skips items where `is_sample`, `includes_tester`, `state === "CANCELED"`, or `order_item_type !== "PRODUCT"`. Price = `wholesale_price.amount_cents / 100` — this is the B2B wholesale price the retailer pays (Faire is wholesale-side; `retail_price` is the suggested resale RRP, not what's charged). Quantity = `item_quantity * (unit_multiplier || 1)`. **Category is taken from Faire's native `json.products[item.product_token].taxonomy_type.group_name`** (e.g. "Robes", "Pantalons", "Jupes", "Bagues"), then **normalized via `normalizeFaireCategory`** so that every bijouterie sub-family collapses into a single generic label: `Bague` (matches "Anneaux et bagues à empiler", "Bague avec plusieurs pierres", "Grosses bagues", "Solitaires"…), `Boucles d'oreilles` (matches "Boucles d'oreilles pendantes", "Créoles", "Clous d'oreilles"…), `Collier` (matches "Colliers à pendentifs", "Colliers maillons et chaîne", "Sautoirs et colliers en Y"…), `Bracelet` (matches "Bracelets à charms et breloques", "Bracelets à maillons et chaînes", "Bracelets de perles"…), `Parure de bijoux`. Non-jewelry labels ("Robes", "Supports et présentoirs à bijoux"…) pass through unchanged. `group_name` is the middle tier of Faire's 3-level taxonomy (`name` > `clean_name` > `group_name`) and is the cleanest match for the user's internal classification — the more granular `name` field ("Solitaire", "Anneau/bague à empiler"…) was rejected as too fine. Falls back to `detectCategory(item.product_name)` only when `taxonomy_type.group_name` is absent (result also runs through `normalizeFaireCategory`). Order number for display: `brand_order.token` with the `bo_` prefix stripped and uppercased. Verification total: `item_subtotal.amount_cents / 100`. The `samples/faire-ordre.json` file is a real captured response used for offline testing; it's not used at runtime.
- **Microstore** `parseMc`: walks `json.data.doc_info.goods_info[]`. Skips items where `disable === "1"` or `status === "0"`. Numeric fields all arrive as **strings** so `parseFloat` / `parseInt` are required: `price = parseFloat(item.price)`, `qty = parseInt(item.quantity, 10)`. **Category is derived via `detectCategory(item.name)`** (same rationale as Faire — Microstore's `category_name` like "Lot de bracelets avec présentoir" is intentionally ignored). Order number = `doc.number`. Verification total = `parseFloat(doc.total_price)`. The JSON comes from the intercepted `pluginsWeb/orderInfo/{id}` response (not a direct fetch — see `injected-mc.js` above).
- **Orderchamp** `parseOc`: runs on the order detail page (`/{locale}/backoffice/orders/{numericId}`) and reads the DOM directly — no fetch. Finds every `<a href*="/backoffice/products/">`, walks up to the enclosing `<tr>`, dedupes by row (the row has both an image `<a>` and a text `<a>` pointing to the same product), then locates the cell whose text matches `\d+\s*x\s*[\d\s.,]+\s*€` to extract the quantity and the **discounted** unit price (`text-striked-through` siblings are present but the regex captures the first euro amount only). **Category is derived via `detectCategory(name)`** (consistent with Faire/MC; Orderchamp doesn't expose a usable category). Order number is read from the page `<title>` (`/OC\d+/`). Verification total is the `<tr>` whose first `<td>` text equals `"Total"` in the totals table. Helper `parseEuroAmount` normalizes both `"5,40 €"` (decimal comma) and `"1 234,56 €"` (thousands space).
- **Shopify** `parseShopify`: walks `order.lineItems.edges[].node`. Quantity prefers `currentQuantity` (post-refund) over `quantity` (original) — if you need original instead, flip this. Price = `originalUnitPriceSet.shopMoney.amount` parsed with `parseFloat` (string in GraphQL). **Category is derived via `detectCategory(node.title)`** (same rationale as the other DOM/no-native-category sites). Order number = `order.name` (Shopify's `#1234` style). Verification total = `order.subtotalPriceSet.shopMoney.amount`. The endpoint requires both `storeName` (from `/store/{name}/orders/{id}`) and a captured CSRF token — without one of them, the background returns a typed error without firing the request.
- **Beli & Jolie** `parseBj`: walks `json.items[]`. Price = `it.prixUnitaire`, quantity = `it.quantite`, category = `it.categorie` (already resolved server-side from `Product.category.name`). **PACK detection is DOM-based**: the API only ships raw `{quantite, prixUnitaire}` (pack-price × nb-packs for PACK lines), so `readBjPackInfoFromDom` scans every `<td>` for text matching `/Pack\s*×\s*(\d+)/`, walks up to the enclosing `<tr>`, then reads two sibling cells: qty (idx+1) and unit price (idx+3). Both cells may show `ancien → nouveau` after admin edits — the parser takes the **last** integer / last € amount to get the current effective value. Extracted entries are matched to API items by `(qty, unitPrice)` with 0.01 € tolerance; on match, the item is split as `qty × packQty` at `unitPrice ÷ packQty` (same shape as PFS's PACK handling). Matches are consumed FIFO via a `used` flag so two API items with the same (qty, price) don't collide onto the same DOM entry. Order number = `json.orderNo`. Verification total = `json.subtotalHT`. Addresses via `bjAddrToFields` from `json.shipping` / `json.billing`. **If the DOM shape changes** (row td order, "Pack × N" wording), PACK lines will silently fall back to displaying the raw pack price — the button won't error, so keep an eye on the aggregated total matching `subtotalHT` after any admin-page refactor.
- **Bijoux Mystères** `parseBm`: walks `data.items[]`. Price = `it.unitPrice`, quantity = `it.quantity` (already numeric — no parseFloat needed but done anyway defensively). **Category comes directly from `it.categoryName`** (native, cleanly labeled — "Boucles d'oreilles", "Collier", etc.), falling back to `detectCategory(it.name)` if missing. Order number = `data.orderNumber` (like `CMD-2026-000022`). Verification total = `data.totalHT` (already HT, matching the sub-total HT computed by the modal). Addresses use `bmAddrToFields`: company/contact/SIRET/VAT/email are read from `data.customer` (which is shared between shipping and billing since it's the account holder), while street/zip/city/country/phone are read from the address block itself. The `label` field on the address is only used as a fallback company name when `customer.companyName` is missing (label is typically a nickname for the address, not the legal company).

Note on `detectCategory` regexes: they must handle both apostrophes (`'` U+0027 and `’` U+2019 — Faire's `product_name` uses the typographic variant) and plurals (e.g., `cha[îi]nes?` matches both "Chaîne" and "Chaînes"). The function covers two universes: **bijouterie** (Boucles d'oreilles, Bracelet, Bague, Collier, Pendentif…) and **prêt-à-porter** (Robes, Ensembles haut et pantalon/jupe/short, T-shirts, Pantalons, Jupes, Shorts, Chemisiers, Chemises, Tops, Blazers, Vestes). Order is critical: clothing patterns sit **before** `collier`, so a "Top détail dentelle avec collier" stays classified as `Tops`. `Robe` is checked before `chemise` / `t-shirt` so "Robe chemise" / "Robe t-shirt" classify as `Robes`. `Ensembles` does sub-detection (jupe > pantalon > short) to mirror Faire's `group_name` labels. When adding a new heuristic, put more-specific patterns before more-general ones (the function returns on first match), and prefer plural labels matching Faire's `taxonomy_type.group_name` for cross-site consistency. Sites without a usable native category field (`aks`, `mc`, `oc`, `shopify`) all rely on this single function.

## UI

`modal.css` is loaded via `manifest.json` `content_scripts.css` and uses `#pfs-*` / `.pfs-*` IDs and classes throughout to avoid colliding with the host page. The button and overlay use `z-index: 2147483646/7` for the same reason. DOM is built imperatively via the local `el(tag, props, children)` helper in `content.js` — no framework.

Address rows are rendered as a 3-column grid (`140px 1fr auto`) where the third column is a per-line **copy-to-clipboard button** built by `makeCopyButton(value)`. The button SVGs are constructed via `document.createElementNS` (not `innerHTML`) to satisfy a security hook in the dev environment that blocks `innerHTML` writes. Label-less rows (notes like "Voir l'iPad" or "Identique à l'adresse de livraison") span both columns and get no copy button. **All labelled values are uppercased** at render time via `.toLocaleUpperCase("fr-FR")` (accents preserved: é→É, etc.) — applies to every marketplace and every field type (société, contact, adresse, CP, ville, pays, téléphone, email, SIRET, TVA…). The copy button copies the uppercased text too, so paste-into-invoice keeps the same casing. Label-less notes stay unchanged.

The rows table repeats the category on every line (no row-spanning cell) and alternates the row background per **category group** via `pfs-cat-a` (white) / `pfs-cat-b` (gray) classes — the parity index `groupIdx` is bumped only when the category changes, so all rows of one category share a color.

### Sage 50 CSV export

The modal footer has an "Exporter CSV Sage" button (`#pfs-sage-btn`, handler `exportToSageCsv`) next to the PDF one, available on every site since it only consumes the normalized `rows`. It downloads `sage_facture_{orderNo}.csv` in the exact shape of the user's saved Sage 50 "Import des pièces" paramétrable format: 10 semicolon-separated columns (`TypeLigne;TypePiece;NumPiece;DatePiece;CodeClient;CodeArticle;Quantite;PUHT;TauxTVA;Description` — mapped in the Sage format to Type de ligne / Doc Type de pièce / Doc N° pièce / Doc Date Pièce / Doc Code Tiers / Lg Article / Lg Qté / Lg Prix Uni. HT / Lg Tx TVA / Lg Description), one title line (declared as "1 ligne à ignorer" in Sage), CRLF line endings, decimal comma, date `JJ/MM/AAAA`. L lines are aggregated per `(code, price, ref)` — not per code+price — and `Description` is multi-line: first line `"{LABEL UPPERCASE} - {ref}"`, then one line per color `"{Couleur} x{qty}"` (colors French-ified + capitalized via `formatColorFr` and its `SAGE_COLOR_FR` EN→FR dictionary — Golden→Doré, etc.). ### Hidden behavior (Easter egg)

The modal footer contains a horizontal strip of seven 18×18 images at `opacity: 0.35` (`#pfs-img-strip` / `.pfs-mini-img`). Their order is randomized at modal-creation time via Fisher–Yates. Only `z.png` has a click handler (`onSecretImgClick`); the six `img1..img6.png` are pure decoys with no listener — none of the seven shows a `cursor: pointer` so nothing visibly signals which one is live. Clicking `z.png` increments `_secretClickCount`; the multiplier is `getSecretFactor(clicks) = clicks < 3 ? 1 : 2 + Math.floor((clicks - 3) / 2)` — i.e. ×2 at click 3, then +1 every 2 further clicks (×3 at 5, ×4 at 7, …). `renderRowsTable()` rebuilds the table from `_originalRows` (never from the currently-displayed values, so divisions don't compound) with `quantite * factor` and `prixUnitaire / factor`. Both counters reset on every `showModal` call, so reopening the modal restarts at ×1.

Practical note for refactors: `_originalRows` and `_secretClickCount` are **module-level state** in `content.js`. The footer / image strip is built once in `ensureOverlay` (modal is a singleton); `showModal` only repopulates the body. If you split the modal into separate component files, keep both the originalRows snapshot and the click counter at a level that survives table re-renders.
